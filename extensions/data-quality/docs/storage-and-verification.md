# Storage and verification boundaries

Configuration version 2 is stored in the current account's saved filters under `ext:com.midnightrider.data-quality:configuration`. The canonical record is named `Data Quality configuration`. It contains complete reviews, their unchanged review/action IDs, a revision token, imported-ID history, and deletion tombstones. Reviews without `entityType` are interpreted as videos; new reviews store `video`, `audio`, `tag`, `performerOccurrence`, or `audioPerformerOccurrence`. The audio entity types are rejected in a saved review that also carries the multiple-item layout or grid-only presentation, which no audio review renders. Video actions retain ordered `steps`; tag actions store one `effect` that sets a group, clears it, or skips. Progress version 1 uses `ext:com.midnightrider.data-quality:progress`, one record per review. The extension never bypasses Cove authentication or authorization.

The newest existing account-scoped browser snapshot is authoritative during initial prototype adoption, including an empty array. Older snapshots supply migration history, not deleted reviews. Account-imported reviews are adopted once. Tombstones prevent a later browser from reviving deleted imports. The unscoped `page-videos` key and its import/deletion history have no trustworthy owner: they are never automatically copied to an account. The review page offers an explicit recovery export for manual import into the intended account. Original prototype keys remain untouched for recovery; the extension no longer writes them. Differing local/account edits with the same ID stop migration without overwriting either version and expose an account-scoped browser recovery download. Nonconflicting browser-only reviews can migrate when storage permissions are granted. Unknown versions and malformed data are retained and reported, not reset.

Initial loads share a single in-flight request. Identical duplicate first-install records are preserved under recovery names, with the lowest record ID retained as canonical. Conflicting duplicate account records require explicit reconciliation; the extension never picks one silently. Configuration saves are serialized within the browser and compare the remote revision before writing. A stale draft stays open and can be exported. Cove does not expose conditional writes or transactions through this API: two browsers writing at precisely the same time may still overwrite one another after both revision checks pass. Avoid concurrent editing; reload to receive another browser's saved configuration. This is a documented public-API boundary, not an atomicity guarantee.

Progress saves contain queue signature, normalized page and page size, focused entity ID and its index, current view, and card width. Legacy video queue signatures are unchanged; tag signatures include the entity type. The browser cache updates after settled navigation; account writes follow a 600 ms debounce. Sync failures keep browser caching active and offer retry. Closing a browser before account synchronization finishes can leave the other browser at its previous checkpoint. Progress does not restore selection or reopen the player. Temporary queue adjustments do not overwrite saved-queue progress.

Resume first checks the saved queue signature. Changed filters, search, sort, or page size restart at page one. An unchanged queue resumes its saved page, clamped to the new last page, and focuses the saved video if it is on that page; otherwise it uses the saved index, clamped to available results. It does not scan an entire library to locate an item that moved to another page. Empty results clear focus. A newer local checkpoint can recover an unsynchronized session. Concurrent reviewers use the latest successful progress write; progress is a checkpoint, not a review-completion ledger.

Account storage needs `savedfilters.read` and `savedfilters.write`. Read without write exposes configuration read-only; temporary filters remain usable. Without read permission, configuration and progress remain browser-only and the UI states that limitation. Video actions need `videos.write`; audio actions need `audios.write`; tag-group actions need `tags.write` and group resolution needs `taggroups.read`. Preview/query access continues to use Cove's existing entity permissions. Tag bins, annotation hierarchies, and descendant removal also need tag read access. Tag assessments additionally need `system.read` to inspect custom-field definitions. The explicit setup action requests the key `confirmed_absent_tags` through the existing custom-field creation endpoint and therefore needs `system.settings.write`. A compatible existing definition is reused; a missing definition blocks assessments until setup succeeds, while an incompatible definition must be corrected in Cove settings. One definition serves both media kinds: a definition that applies only to videos is extended to audios through the same setup action, which adds the media kind to its existing entity types rather than replacing them, so recorded video assessments are preserved.

Hierarchy failures are reported, and every descendant action step in an assessment action resolves before any video write. Every action step, legacy or assessment, is then one authorized bulk request for all selected videos, with legacy add and remove steps sent before assessment steps. An assessment step pairs the tag change with the `confirmed_absent_tags` custom field in that same request: marking present adds the tag and removes it from the field, marking absent removes the tag and adds it to the field, and clearing absence only removes it from the field. Cove merges the field values server-side, so no per-video read or rewrite happens, unrelated custom fields are never resent, and videos whose values already match are left untouched. A failed step stops the remaining steps without rollback or automatic retry and reports how many earlier steps completed. Cove rejects the whole step, applying nothing, when the field is unknown, not defined for videos, or given a value that is not a tag id. Cove caches identical filtered queries for one second and exposes no public invalidation hook, so metadata actions remain pending for approximately 1.1 seconds before refreshing membership after either success or partial failure. Skip does not wait.

Queues honor Cove's native finite page-size choices through 1,000 videos and abort superseded requests. Wall previews load near the viewport and play only while visible. Bins enumerate descendant tags present on the loaded page; their counts are page counts, not library-wide aggregates. A bin adds a temporary AND condition while retaining existing filters. Native Cove cards omit video descriptions and show only the date, studio, performers, and tags explicitly selected as card annotations. Tag annotations show only descendants of one or more configured parent tags and remain hidden when no parent is configured. Cards with no applicable annotations omit the empty metadata row, popover footer, and divider.

The production UI and package must be rebuilt after changing source. Verification uses the extension's Vitest suite, its Release solution build and focused C# manifest test, Cove's production UI build, the development package validator, installation through `cove-install-extension`, and live UI workflows. Culture staging is the populated workflow reference; task-local Culture exposes the editor but its backing Stash result calls failed during this task. Neither observation is substituted for the other.

## Filter-driven media workspace

Video and performer occurrence reviews now ignore the legacy progress records described above. Those records remain untouched for compatibility; only tag-group reviews continue to use their progress workflow. Media review queries are serialized completely in the URL, including explicit empty criteria and `performerScope`. The compact reset control reads current review defaults; the adjacent save control explicitly updates the review's queue criteria. Local tag drafts live only in the open workspace and are never written as progress.

## Performer occurrence assessments

Cove attaches custom fields to whole entities, so a performer occurrence cannot own one. Occurrence reviews therefore record confirmed absences on the video in a second custom field, `confirmed_absent_occurrence_tags`: a filterable, multi-value text field for videos whose values are `<performerId>:<tagId>` pairs. It is separate from `confirmed_absent_tags` because a video-level absence is a stronger claim than one performer's. The setup action appears only on occurrence reviews that contain an assessment step, creates the field through the same endpoint, and needs `system.settings.write`. Applying assessments needs `system.read`, `tags.write` for the occurrence tag, and `videos.write` for the pair; assessment actions stay disabled until the field is ready and video write access is present, while plain tag actions in the same review keep working.

The field is verified before any write, so a missing or incompatible definition changes nothing. Marking absent removes the performer's tag application and then adds the pair; marking present removes the pair and then adds the application; clearing absence only removes the pair. Within one assessment step each order leaves an unassessed occurrence, never a recorded absence beside the tag, if the second request fails. As with video reviews, a plain add step, the tag editor, or a batch can later add a tag without clearing its pair; the workspace then shows the tag and its confirmed absence together until an assessment corrects it. The pair is one bulk request with `customFieldMode` `ADD` or `REMOVE`, so Cove merges it server-side and other performers' pairs on the same video are never read or resent. Batches change tags only and do not offer assessment actions.

A queue whose occurrence condition is "Has none of the selected tags" hides an occurrence once every selected condition tag is confirmed absent for that performer. Absences are matched by exact tag id, so an assessment step should name the same tags the condition selects; an absence recorded for an ancestor or descendant does not hide anything, and marking a parent absent does not remove the occurrence's subtags. "Hide occurrences confirmed absent" is on by default and is part of the saved queue criteria and the `performerScope` URL value. When the queue targets exactly one performer and one condition tag, the pair is sent to Cove as a "no value equals" custom-field criterion, so answered scenes leave the result set and its count. Every other shape may still hold an unanswered occurrence in the same scene, so it is hidden in the browser after Cove pages the scenes: pages get shorter, Cove's scene count is unchanged, and opening a queue walks past pages with nothing left to review. Batch previews apply the same hiding and say so. Pairs are plain text without referential integrity: values that are not pairs are ignored, and merging or deleting a tag or performer leaves stale pairs, which are inert but remain visible as raw values on the video's custom fields.
